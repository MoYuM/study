- ESM：静态导入（编译时确定依赖）、支持 Tree-shaking、可异步加载、import/export，是值引用（活绑定）、不存在循环引用问题（CJS 循环引用时可能拿到未执行完的模块导出的不完整对象）。
- CJS：运行时同步加载、require/module.exports、动态、不易 Tree-shaking，是值拷贝。

## 发展史（问题 → 方案的链条）

**❓ 2009 年之前，JS 没有模块系统，所有代码共享全局作用域**
浏览器脚本没有原生模块机制，多个 `<script>` 标签的变量都挂在全局对象上，项目一大容易互相覆盖、命名冲突。

**✅ IIFE / 命名空间对象：靠约定手动模拟"模块"**
开发者用立即执行函数表达式把代码包在闭包里避免全局污染——这只是编码约定，没有正式的依赖声明和加载机制。

**❓ IIFE 解决了作用域污染，但没法声明依赖关系，也没法异步加载**
多个 IIFE 之间的依赖顺序全靠开发者手动排列 `<script>` 标签，容易出错。

**✅ CommonJS（2009 年 1 月由 Kevin Dangoor 发起，最初叫"ServerJS"，同年 8 月改名）：为服务端 JS 定义同步模块规范**
`require()`/`module.exports` 专为服务端设计——文件都在本地磁盘，同步加载没有网络延迟问题。同年 5 月发布的 Node.js 借鉴/实现了这套 CommonJS 风格的模块系统（并非 100% 照搬规范文本，后续两者在细节上有分歧）。

**❓ CommonJS 是同步的，直接搬到浏览器会阻塞页面（模块要通过网络请求获取）**
浏览器里如果每次 `require` 都同步等待网络请求，页面会被卡住。

**✅ AMD（起源于 2009 年，RequireJS 2011 年 10 月发布 1.0 成为代表实现）：专为浏览器设计的异步模块加载**
AMD 用 `define()`/`require()` 加回调的方式异步加载模块——RequireJS 项目本身也诞生于 2009 年，但作为成熟、被广泛采用的实现，要到 2011 年 1.0 版本发布才算真正落地。

**❓ 服务端用 CommonJS、浏览器用 AMD，两套不兼容的模块系统并存**
同一份代码想同时在 Node 和浏览器跑，得写 UMD 胶水代码，或者靠 Browserify（2011 年 2 月发布）这类打包工具把 CommonJS 代码转换成浏览器能跑的格式。

**✅ ES2015（2015 年 6 月）正式标准化 ESM：静态、可分析的原生模块语法**
`import`/`export` 被写进语言规范本身，且必须写在模块顶层（不能放在条件语句里动态拼接路径），这个"静态"约束让工具能在不运行代码的情况下分析出完整依赖图，从而支持 Tree-shaking。

**❓ 静态 import/export 必须写在模块顶层，没法"按需/条件加载"某个模块（比如路由懒加载）**
静态 import 不能放进 `if` 语句或函数调用里按需触发，意味着所有静态导入的模块都会在启动时一起被解析加载，没法做到"用到才加载"。

**✅ 动态 `import()`（TC39 提案 2016 年 9 月启动，2019 年 6 月达到 Stage 4，正式写入 ES2020；浏览器实现更早：Chrome 63/2017 年 12 月、Safari 11.1/2018 年 4 月、Firefox 67/2019 年 5 月）：返回 Promise 的按需导入表达式**
`import('./foo.js')` 可以写在任意位置（包括 `if` 语句、事件回调里），返回一个 Promise，实现懒加载/代码分割——这也是"提案到 Stage 3 阶段浏览器就抢先实现，早于正式规范发布"的一个典型例子。

**❓ 动态导入的参数不再是"静态可分析的顶层声明"，会不会让 Tree-shaking 失效？**
`import()` 的参数理论上可以是任意运行时表达式，打包工具没法像分析静态 import 那样，总能精确知道会加载哪个模块、用了它的哪些具名导出。

**✅ 分场景看：参数是静态字符串时，chunk 内部 tree-shaking 依然有效；但调用方用了动态模块的哪些具名导出，通常无法被精确裁剪**
如果 `import('./foo.js')` 的参数是静态字符串，打包工具依然能识别出目标模块，把它和自己的静态依赖子图打成独立 chunk——chunk **内部**基于静态 import/export 的 tree-shaking 完全不受影响。但调用方是通过 `const { a } = await import('./foo.js')` 这样对返回的 Module Namespace Object 做运行时属性访问/解构，而不是声明式的静态绑定，多数打包工具无法据此反推"这个动态模块里 b、c 没被用到、可以裁掉"。**动态 import 换来的是"按需加载"的代码分割能力，代价是牺牲了对该模块未使用具名导出的精细裁剪**——如果参数是运行时变量（如 `import(someVariable)`），连目标模块本身都无法静态确定，则完全谈不上任何构建期分析。

**❓ 规范定案后，Node.js 对原生 ESM 的实际支持花了好几年才跟上**
Node.js 实验性支持 ESM 从 **v8.5.0（2017 年 9 月）** 开始（需加 `--experimental-modules` 标志），直到 **v13.2.0/v12.17.0** 才去掉实验标志，稳定支持要到 2020-2021 年前后。

**现状：ESM 是现在的标准方向，CJS 因历史生态仍广泛留存；动态 import() 补上了按需加载能力，但引入了"chunk 级 tree-shaking 仍有效、具名导出级裁剪打了折扣"的新权衡**

## 活绑定 vs 拷贝

ESM 导出的是**活绑定**（live binding）：导入方拿到的是对原始变量的引用，源头变了它跟着变。

```js
// counter.mjs
export let count = 0
export function inc() { count++ }

// main.mjs
import { count, inc } from './counter.mjs'
inc()
console.log(count) // 1 ← 跟着变了
```

CJS 导出的是**值拷贝**：`require` 时复制一份快照，源头之后的变化不影响已拿到的值。

```js
// counter.js
let count = 0
function inc() { count++ }
module.exports = { count, inc }

// main.js
const { count, inc } = require('./counter')
inc()
console.log(count) // 0 ← 还是旧值（拿的是拷贝）
```

**坑**：用 CJS 时如果想拿到最新值，要每次重新 `require().count`，或导出函数而非值。
