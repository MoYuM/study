模块联邦（Module Federation，Webpack 5，2020）：让多个独立构建的应用在**运行时**互相加载对方的模块（host/remote），共享依赖，无需重复打包。核心突破是"运行时"而非"构建时/npm 发包"——remote 代码更新，host 下次加载就是最新版本，不用走发布流程。是微前端架构下解决"代码共享"这个子问题的主流技术方案之一。

## 发展史（问题 → 方案的链条）

❓ 微前端（术语最早见于 2016 年 11 月 ThoughtWorks Technology Radar）架构下，多个独立团队各自开发部署自己的子应用，怎么共享代码？最早的方案是发 npm 包。
✅ npm 包能用，但迭代慢：代码一改就要重新发版 → 各消费方重装依赖 → 重新构建 → 重新部署。

❓ 也有团队用 iframe 隔离子应用，这样更好吗？
✅ iframe 隔离强，但跨 iframe 通信麻烦（`postMessage`）、共享状态难、性能和 SEO 都打折扣。

❓ 能不能让独立构建的应用在运行时直接互相加载对方模块，不用 npm 发包流程，也不用 iframe 隔离代价？
✅ Zack Jackson（Webpack 维护者）提出 Module Federation，2020 年作为 Webpack 5 旗舰特性发布（与 Marais Rossouw 共同开发，Tobias Koppers 指导）。

❓ Module Federation 最初绑死在 Webpack 上，团队想用 Vite/Rspack 怎么办？
✅ 约四年后（2024 年前后），Module Federation 2.0 把运行时从 Webpack 剥离成独立库，Rspack、Vite 都能原生支持，不再被单一构建工具锁死。

**现状**：PayPal、Shopify、Adidas、字节跳动等公司在生产环境使用；Spotify 用它把桌面播放器拆成播放器/导航/艺人页等可独立发布的模块。

## 微前端还有哪些主流方案（不止 Module Federation）

- **qiankun（乾坤）**：蚂蚁金服"云产品统一前端平台"孵化，基于 single-spa 增强（JS 沙箱 + CSS 隔离），已服务蚂蚁内部 2000+ 线上应用，是国内最常见的方案之一。
- **single-spa**：2016 年诞生于 Canopy Tax，路由级微前端元框架，负责多个不同框架（React/Vue/Angular）子应用的挂载/卸载，不管代码共享（qiankun 就是在它基础上加了沙箱增强）。
- **服务端组合式（Zalando Mosaic/Tailor）**：2015 年 Zalando 从单体应用迁移时提出，不在浏览器拼模块，而是服务端把各团队的页面片段（Fragment）拼成完整页面。Zalando 目前已演进到新架构"Interface Framework"，Mosaic 不再是其现在的主力方案，只是"服务端拼接"这个思路的开创者。
- **Native Federation**：Angular Architects 团队（Manfred Steyer）提出，用浏览器原生 ES Modules + Import Maps 实现同样效果，不绑定任何构建工具，是跟 MF2.0（脱离 Webpack 锁定）同一个问题的另一种解法。

## qiankun 与 Module Federation 的原理差异

| | qiankun | Module Federation |
| --- | --- | --- |
| 加载单位 | 整个应用（抓取完整 HTML 入口，执行全部 JS，调用 bootstrap/mount/unmount 生命周期） | 单个模块（host 拉取 remote 的 `remoteEntry.js` 清单，按需请求具体模块的 factory，调用时才真正下载执行） |
| 隔离哲学 | **主动隔离**：JS 沙箱（ProxySandbox 给子应用造"假 window"等）+ CSS 隔离，防止各自以为独占全局环境的子应用互相污染 | **主动协作**：`shared` + `singleton: true` 让 React/ReactDOM 等核心库在 host/remote 间协商出同一份实例，避免多实例导致 hooks 失效 |
| 适用场景 | 整合多个历史遗留的、互不信任的完整应用 | 细粒度共享具体组件/业务逻辑，避免依赖重复加载 |

两者不是互斥关系，可以叠加使用：得物技术团队的真实实践是"qiankun 做应用级路由挂载和隔离外壳 + Module Federation 做模块级代码共享"。
