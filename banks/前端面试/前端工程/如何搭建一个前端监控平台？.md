三大模块：**采集 → 上报 → 存储/处理/告警**

## 采集

| 类型 | 采集方式 |
|------|---------|
| JS 错误 | `window.onerror`（同步错误）、`unhandledrejection`（Promise 未捕获）、框架 `ErrorBoundary` |
| 资源错误 | `addEventListener('error', handler, true)`（捕获阶段，img/script 加载失败） |
| 性能 | `PerformanceObserver` + Web Vitals（LCP / CLS / INP） |
| 行为埋点 | 点击事件、曝光（`IntersectionObserver`）、自定义业务埋点——见下方"埋点分类" |

## 追问：为什么资源错误（img/script 加载失败）必须用捕获阶段监听，而不是 `window.onerror`？

`window.onerror`/普通冒泡阶段的 `error` 事件监听器捕获不到资源加载错误——**不是因为要用 `unhandledrejection`**（那是 Promise 被 reject 但没人 `.catch()` 的机制，跟资源加载完全是两回事），而是因为**资源加载错误事件不会冒泡**。img/script 的 `error` 事件只在目标元素上触发，不会向上冒泡到 window，所以常规的冒泡阶段监听收不到。解决办法是 `window.addEventListener('error', handler, true)`——第三个参数 `true` 让监听器工作在**捕获阶段**，捕获阶段是从 window 往下派发，不受"是否冒泡"限制，能在事件到达目标元素之前先拦截到。

三条独立的监听机制，容易混：
- `window.onerror`：同步 JS 运行时错误
- `unhandledrejection`：Promise 被 reject 但没人 `.catch()`
- `addEventListener('error', handler, true)`（捕获阶段）：img/script 等资源加载失败

## 埋点分类（行为采集的三种方式）

- **手动埋点**：业务强相关，手动在代码中插点，精确但维护成本高
- **自动埋点（无埋点）**：全局监听事件/错误自动采集，覆盖广但数据冗余
- **可视化埋点**：运营在界面上圈定元素，不改代码，灵活但依赖平台

## 上报方式对比

| 方式 | 跨域 | 页面关闭后 | 特点 |
|------|------|-----------|------|
| `sendBeacon` | ✅ | ✅ **仍可上报** | 浏览器异步发送，**POST**（不能自定义请求头），不阻塞页面，专为卸载时上报设计；**局限**：数据量有限（几十 KB 级别）、无法读取响应内容——纯粹"发出去就不管了"，不适合需要响应结果的场景 |
| 图片打点 `new Image().src=url` | ✅ | ❌ 会中断 | 最简单，**GET**，数据量受 URL 长度限制 |
| `fetch` | ✅ | ❌ 会中断 | 灵活，可 POST 大数据，但页面关闭时请求被取消 |

> beacon 优先：应该监听 `visibilitychange`（而不是 `unload`）触发上报——现代浏览器（尤其移动端）有 bfcache（back-forward cache）机制，页面被放入 bfcache 时 `unload` 不一定触发或不可靠；`visibilitychange` 在页面切到后台/隐藏时就能可靠触发，时机更早也更稳。`visibilitychange` / `beforeunload` 时机的上报必须用 beacon，它是唯一能可靠发出的方式，兼容性不足时降级 `new Image()`。

**上报最佳实践：** 批量上报（本地队列攒批，空闲时发送）+ 采样（不是每条都报，降低服务器压力）+ 失败重试

## 后端处理

- **SourceMap 还原**：生产环境代码压缩后堆栈是 `bundle.min.js:1:123456`，必须用 SourceMap 映射回源码行列
- **聚合去重**：相同错误合并计数，避免告警风暴
- **告警阈值**：错误率/PV 超阈值触发通知
- **看板**：错误趋势、设备/版本分布、用户影响范围

## 核心原则

低侵入、不影响主流程性能、数据可定位到用户与版本。

## 发展史（问题 → 方案的链条）

这部分聚焦"上报"这个环节——它是监控平台里最早出现、也最有真实设计演化史的一块。

**❓ 网站主想知道有多少人访问、看了什么，但最早只能看服务器日志**
1990 年代最早期的网站分析靠解析 Web 服务器的访问日志（Apache/IIS access log），按请求记录统计访问量。

**❓ 服务器日志看不到客户端行为，缓存命中的页面甚至根本不会打到服务器**
日志只能反映"服务器收到了哪些请求"，浏览器本地缓存命中时压根不发请求，更没法知道用户点了什么、滚动到哪。

**✅ 1x1 像素追踪图（web beacon）：不管有没有缓存，都强制发一次请求**
在页面里嵌一个指向分析服务器的 1x1 像素 `<img>`，利用图片请求天然跨域、又能绕开缓存的特点，让分析服务器每次都能收到"页面被打开了"的通知。2005 年 Google 收购 Urchin 推出 Google Analytics 后，"JS 脚本 + 追踪像素"成为主流标准做法。

**❓ 像素请求只能算"页面加载了一次"，没法携带丰富的自定义业务事件**
简单的图片请求本质是一次 GET，能带的数据有限，没法表达"用户点击了哪个按钮、提交了什么表单"这类结构化业务事件。

**✅ 用 XHR/fetch 发送结构化事件数据**
借助 AJAX，把业务事件包装成 JSON 通过 XHR/fetch 发给分析服务器，能捕获任意自定义业务埋点，不再局限于"页面加载"这一种事件。

**❓ 但 XHR/fetch 请求在页面即将关闭（卸载）时经常被浏览器直接中断，数据发不出去**
用户跳转或关闭标签页时，卸载过程中的普通 XHR/fetch 请求很容易被浏览器取消，导致最后一批关键数据（比如错误堆栈、页面停留时长）丢失。

**✅ Beacon API（规范草案与 Chrome 39 的实现都在 2014 年，主流浏览器普及要到 2018 年前后）：专门保证卸载阶段也能把数据发完**
`navigator.sendBeacon()` 让浏览器把上报请求放进异步队列，即使页面开始卸载也能保证请求发送完成、且不阻塞卸载过程。

**❓ 埋点/错误/性能数据量上来后，全量上报会打爆监控服务器、拖慢页面；2018 年 GDPR 生效后随意采集用户数据还可能违规**
高流量场景 100% 上报会给监控服务器和用户网络带来明显负担；GDPR（2018 年 5 月生效）等隐私法规也对采集哪些用户数据、如何取得同意提出了明确合规要求。

**✅ 工程化对策：采样、批量上报、隐私合规审查**
现代监控平台普遍加上采样率控制（不 100% 上报）、本地队列攒批再发送、以及对敏感信息的过滤/脱敏。

**现状：Beacon 优先、Image 兜底的上报方案，外加采样/批量/合规三件工程套件——这套上报层基础设施是错误监控、性能监控、行为埋点共用的，不需要为每种数据类型各造一套**

## 业界现状：主流监控框架怎么做

**上报机制对比**

| 产品 | 主上报方式 | 兜底/替代 | 卸载/隐藏触发时机 |
|---|---|---|---|
| Sentry | `fetch` | 旧版 XHR | `visibilitychange` |
| 阿里云 ARMS | sendBeacon（行业文章描述，官方未明说完整策略） | 图片打点 `new Image` | 官方未明说 |
| 腾讯云 RUM(Aegis) | `sendBeacon`（官方明确） | 降级 `new Image` | 官方未单独说明 |
| Datadog RUM | `fetch(keepalive)` | 退出时回退 `sendBeacon`，大批量走 XHR | 显式监听 `visibilitychange`+`beforeunload`/`pagehide` |
| LogRocket | `sendBeacon` | 超 64KiB 配额回退无 keepalive 的 fetch/XHR | `visibilitychange` |
| web-vitals（Google 官方） | `sendBeacon` 优先 | `fetch(keepalive)` 兜底 | 明确只用 `visibilitychange`，原文"Never use the `unload` event on modern browsers" |

六家里五家都是 sendBeacon 系（或等价的 fetch keepalive）配合 `visibilitychange` 触发，**Sentry 是唯一的例外**，主动选择 `fetch` 而非 sendBeacon。

**为什么大多数库优先选 sendBeacon，而不是"理论上更灵活"的 `fetch(keepalive:true)`**：

- **普及时间差 10 年**：sendBeacon 是 Chrome 39（2014 年）就支持的老 API；`fetch(keepalive:true)` 直到 Chrome 66（2018 年）才支持，Safari 约 2019 年跟进，**Firefox 更是拖到 2024 年 11 月（Firefox 133）才默认启用**——多年来只有 sendBeacon 是"哪个浏览器都能用"的选择。
- **卸载瞬间的可靠性，fetch keepalive 实测不如 sendBeacon**：Chromium 官方 bug tracker 有明确记录的问题（issue 375903219）——规范要求 keepalive 请求应在页面卸载后继续存活，但 Chrome 渲染进程有时会在卸载时把这个 fetch 请求提前标记为"已取消"；而 sendBeacon 的请求从设计上直接交给浏览器进程接管，不受渲染进程生命周期影响，这正是它"专为卸载场景设计"的原因。
- **请求体限制其实是同一套机制**：容易搞反的一点——两者都限制"所有排队中的请求总和"为 64KB，不是单个请求各自 64KB，且不是 fetch 更宽松。这不是巧合，sendBeacon 底层实现本来就是基于 fetch+keepalive。

**Sentry 的选择反而是特例**：它愿意为了协议层面的两个硬需求——**能读到响应**（判断事件是否被服务端限流/拒绝，从而决定是否重试退避）、**能自定义请求头**（sendBeacon 的 `Content-Type` 只能是几个受限选项，装不下 Sentry Envelope 协议需要的自定义类型）——主动放弃 sendBeacon 更成熟这个优势，赌 fetch keepalive 的可靠性缺口在它的场景里可以接受。

**其他一致收敛点**：
- **SourceMap 还原**：六家清一色是"构建期生成唯一 ID（Sentry 的 Debug ID / 阿里腾讯的 UUID 注入 / Datadog、LogRocket 的 release+version）→ 上传到平台 → 报错时按 ID 精确匹配"，独立设计却收敛到同一套模式。
- **资源加载错误**：都是 capture 阶段监听 `error` 事件，与前面"追问"里的原理一致。
- **Web Vitals**：Sentry 直接封装 Google `web-vitals` 库；Datadog 是**自研实现**（未用 Google 库）；ARMS/腾讯云官方文档目前只明确列出 LCP（ARMS 另有 FID/CLS），INP 支持情况未完整公开。
- **采样率设计不统一**：Sentry `tracesSampleRate`(0~1)、ARMS `pvSample`(1~100 反向)、腾讯云控制台百分比、Datadog `sessionSampleRate`(默认 100% 全量)——同一个概念，五套不同的 API 形态，没有统一标准。
