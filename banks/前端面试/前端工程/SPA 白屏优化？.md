## 发展史（问题 → 方案的链条）

**❓ 传统多页应用（MPA）服务端直接吐出完整 HTML，白屏时间主要看网络和服务端响应速度**
2010 年之前的主流架构下，每次请求服务器都渲染好完整页面再返回，浏览器拿到即可显示。

**❓ SPA 架构兴起后，服务器只返回近乎空的 HTML 壳 + 一个大 JS 包，必须等 JS 跑完才有内容**
2010 年代随着 Backbone/Angular/React/Vue 等框架流行，SPA 把渲染逻辑整体搬到浏览器端——初始 HTML 里几乎没有内容，要等 JS 包下载、解析、执行完，再由 JS 动态渲染出页面，这段等待期间页面是空白的。JS 包越大、首屏要拉的数据越多，白屏越久。

**✅ 代码分割/路由懒加载（webpack 2 于 2016-2017 年引入并普及动态 `import()`）**
把 JS 打包拆成多个 chunk，只在需要某个路由时才按需加载对应代码，减少首屏必须下载/执行的 JS 体积。

**❓ 代码分割只是减少了要等的 JS 量，"必须先跑 JS 才能出内容"这个架构性问题没解决**
即使做了极致的代码分割，首屏仍需要至少加载执行一部分 JS 才能渲染出任何内容，白屏的结构性等待依然存在。

**✅ 骨架屏（Facebook 较早以「content placeholder」推广，后被业界采纳并改名为「骨架屏 / Skeleton Screen」）**
在真实内容渲染出来之前，先用近似最终布局的灰色占位骨架填充页面——不缩短实际加载时间，但能让用户"感觉"页面已经在响应，改善的是**体感**而非真实白屏时长。

**❓ 骨架屏只是体验层缓解，SEO 抓不到内容、真实首屏内容出现时间没变快这两个根本问题没解决**
搜索引擎爬虫抓取时看到的仍是空壳 HTML，用户看到真实内容的时间点也没有提前。

**✅ SSR/预渲染重新回到 SPA 生态（Next.js/Nuxt.js，2016 年前后）**
Next.js（React）、Nuxt.js（Vue）把"服务端直接渲染出完整 HTML"这套 MPA 时代的老方法重新引入 SPA 框架——服务器返回渲染好的内容，首屏不再依赖客户端 JS 执行完才能看到东西，之后客户端 JS 再"水合（hydrate）"接管交互。

**❓ SSR 有自己的代价：每次请求都要服务端渲染，水合过程本身也可能耗时**
SSR 把计算负担转移到服务端，请求量大时压力显著；水合阶段客户端仍需下载执行 JS 才能让页面可交互，复杂页面的水合本身也可能拖慢时间。

**✅ Web Vitals 指标体系（Google，2020 年推出）：用 FCP/LCP 量化定位问题出在哪一环**
Google 在 2020 年推出 Web Vitals 计划，把 FCP（首次内容绘制）、LCP（最大内容绘制）等指标标准化，让开发者能精确测量"白屏具体卡在哪一步"（JS 体积、接口响应、渲染阻塞），而不是凭感觉判断。

**现状：资源层（分包/CDN/预加载）+ 渲染层（骨架屏/SSR）+ 监控层（FCP/LCP）三件套配合使用**

## 优化清单

- 资源层：代码分割/按需加载、压缩、CDN、HTTP 缓存、预加载关键资源。
- 渲染层：骨架屏、SSR/预渲染、关键 CSS 内联、减少首屏请求与体积。
- 监控：用 FCP/LCP 定位，分析白屏原因（JS 体积大、接口慢、渲染阻塞）。
