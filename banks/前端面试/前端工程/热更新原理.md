HMR（热模块替换）：开发时模块代码变更后，通过 WebSocket 通知浏览器，运行时只替换变更的模块，不刷新整页、保留应用状态。

## 发展史（问题 → 方案的链条）

**❓ 每次改代码就整页刷新，慢且丢状态**
早期开发流程里，改一行代码要么手动刷新浏览器，要么工具自动刷新整个页面——不仅慢（要重新加载所有资源、重新执行整个应用），还会丢掉当前的运行时状态（比如填了一半的表单、导航到的深层页面）。

**✅ LiveReload（约 2010 年）：监听文件变化，自动触发整页刷新**
这类工具监听文件系统变化，一旦检测到改动就自动通知浏览器刷新——省去了手动按刷新键的动作，但本质仍是整页刷新，状态照样丢。

**❓ 整页刷新丢状态，对需要反复调整 UI 细节的开发很不友好**
开发 UI 组件时经常需要在某个特定交互状态下反复微调样式/逻辑，每次都要重新操作到那个状态才能看效果，效率很低。

**✅ Webpack 引入 HMR（功能诞生于 2013 年年中，随 2014 年 webpack 1.0 发布后普及）：只替换变更的模块，不刷新整页**
Webpack 的 HMR 机制通过 WebSocket 通知浏览器"哪个模块变了"，客户端 runtime 只替换这一个模块的代码，其余运行时状态（包括其他模块的内存状态）保持不变。

**❓ 但 HMR 需要模块自己知道"怎么用新代码替换自己"，普通业务代码不会主动写这个逻辑**
HMR 提供的是底层 API（`module.hot.accept`），需要开发者在每个模块里手动声明"我知道怎么热替换自己"，普通组件代码不会天然具备这个能力，写起来繁琐——具体机制见下方「核心机制」。

**✅ 框架专属的 HMR 适配层：react-hot-loader → React Fast Refresh**
react-hot-loader（2014 年年中首次发布，2015 年前后随 React 生态流行开来）率先把"组件热替换 + 保留 state"封装成开箱即用的方案；后来 React 官方的 Fast Refresh（约 2019-2020 年被 Create React App / Next.js 等采纳为默认方案）进一步取代了它，不需要手写 `accept`，框架自动识别组件边界完成状态保留的热替换。

**❓ Webpack 式打包在项目变大后，即使只改一个文件，也要基于打包依赖图计算/传输增量补丁，速度会变慢**
无论改动多小，Webpack 都要基于打包后的模块依赖图计算更新补丁，项目规模越大，这个过程的开销越明显。

**✅ Vite（2020 年，尤雨溪发布）：利用浏览器原生 ES Modules，开发时完全跳过打包**
Vite 在开发模式下不做任何打包，浏览器用原生 `import` 直接按需请求模块；文件变化时只需让浏览器重新请求这一个模块，热更新速度不再随项目规模增长而变慢。

**现状：HMR = WS 通知 + accept/dispose 局部替换机制，Vite 用原生 ESM 免打包进一步提速**
无论 Webpack 还是 Vite，底层都依赖"客户端 runtime 局部替换模块 + 保留运行时状态"这套机制；区别只在于变更如何送达浏览器（打包补丁 vs 原生模块请求）。

## 为什么必须用 WebSocket（不是 HTTP）

HMR 需要**服务端主动推送**「某模块更新了」的通知，而 HTTP 只能浏览器发起、服务端被动应答（要主动推只能轮询）。WebSocket 是全双工长连接，服务端可随时主动推，正契合此场景。

## 核心机制：`module.hot.accept` + 冒泡（面试高区分度，常被问漏）

浏览器拿到新代码后，光下载还不够，靠 HMR runtime 完成「局部替换不刷新整页」：

1. **谁接收更新**：一个模块能被热替换，前提是它**自己 `module.hot.accept`**，或它的**某个父模块** accept 了它。
2. **冒泡（bubbling up）**：若改动模块 C 自己没 accept，runtime 往上问「import 了 C 的父模块 B 接不接」，B 不接再往上……一路冒泡直到某层 accept；**若冒泡到入口（entry）都没人接 → HMR 失败，退化为整页刷新**。（这就是「模块不支持局部替换会怎样」的答案。）
3. **替换过程**：所有失效模块先调 `dispose` handler（清理旧副作用、保存要留的状态）→ 卸载旧模块 → 更新 hash → 调用 `accept` handler 用新模块重新执行。
4. **状态为何能保住**：整页没刷新，全局/闭包里的运行时状态本就还在；React/Vue 的热更新插件（如 react-refresh）在 accept 里只替换组件渲染逻辑、**保留组件 state**，故数据不丢。

> 一句话：单个 accept handler 可兜住整棵子模块树的更新——没写 HMR 代码的模块就靠冒泡交给上层处理。
