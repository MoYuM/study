回流和重绘本质上是浏览器渲染页面的步骤之一

浏览器绘制页面的步骤如下：

1. 构建 DOM 树
2. 构建 CSSOM 树
3. 构建渲染树
4. 布局：计算元素的位置、大小
5. 绘制：计算元素的颜色等
6. 合成

- 回流（Reflow）：就是重新跑一遍「布局」，改变几何（尺寸/位置）触发重新布局，开销大。
- 重绘（Repaint）：就是重新跑一遍「绘制」，改变外观但不改布局。
- transform / opacity 是仅有的两个 compositor-only 属性：当元素**已被提升为独立合成层**时，对其做动画可跳过 layout/paint；若未提升仍可能触发 paint。

优化：批量改、读写分离避免强制同步布局、用 class 批量改样式、用 DocumentFragment。

## 追问

### 什么是强制同步布局？为什么危险？

浏览器为了性能会把多次 DOM 修改**批量攒起来**，等空闲时一次性计算布局。但如果你在**写完 DOM 之后立刻读取布局属性**（如 `offsetWidth`、`offsetHeight`、`getBoundingClientRect`、`scrollTop` 等），浏览器被迫立刻刷新队列、重新计算布局才能返回准确的值，这就是**强制同步布局（Forced Synchronous Layout）**。

```js
// 危险：循环里读写交替，每次循环触发一次 reflow
for (let i = 0; i < items.length; i++) {
    items[i].style.width = container.offsetWidth + 'px'; // 读 offsetWidth → 强制 reflow
}

// 正确：读写分离，只触发一次 reflow
const width = container.offsetWidth; // 统一先读
for (let i = 0; i < items.length; i++) {
    items[i].style.width = width + 'px'; // 只写
}
```

会触发强制同步布局的常见属性：`offsetWidth/Height`、`clientWidth/Height`、`scrollTop/Left`、`getBoundingClientRect()`、`getComputedStyle()`。

### 为什么 transform/opacity 能跳过 reflow 和 repaint？

不只是"不触发回流"——transform/opacity 是 compositor-only 属性，元素被提升为独立合成层后，对它做动画可以**同时跳过布局（layout）和绘制（paint）这两步**，直接在合成阶段（compositor thread，很多情况下不占用主线程）重新定位/变换这个已经画好的图层。改 `left`/`top` 会触发回流，回流之后必然还要重新走绘制；transform 把这两步都绕开了，这才是它明显更快的真正原因。

## 发展史（问题 → 方案的链条）

**❓ 早期网页动画只能靠 `setTimeout`/`setInterval` 驱动，时机由开发者自己猜一个时间间隔，不知道浏览器真实的刷新节奏——W3C 规范文档本身指出这个问题：开发者不知道理想更新频率，倾向用很小的 `setTimeout` 值，实际会被浏览器 clamp 到约 10ms，造成不必要的更新**
需要一个跟浏览器真实刷新节奏同步的动画调度 API，而不是靠猜时间间隔。

**✅ `requestAnimationFrame`：Firefox 4（2011 年 3 月，前缀版 `mozRequestAnimationFrame`）、Chrome 10（2011 年 3 月，前缀版 `webkitRequestAnimationFrame`）较早实现，Paul Irish 同年 2 月发文推广这个 API 的用法；规范"Timing control for script-based animations"2013 年 10 月成为 W3C 推荐标准（2015 年 9 月降级为工作组笔记，内容并入 HTML Living Standard）**
动画回调改为跟浏览器刷新率同步触发，不再靠开发者瞎猜时间间隔——但改 `left`/`top` 这类几何属性本身依然会触发完整的 layout+paint，没有解决"改属性开销大"这个根本问题。

**❓ 即便动画时机精确了，如果每帧都要重新走 layout+paint，复杂页面在低性能设备上还是容易掉帧**
需要把动画属性从"每帧都要重新计算布局绘制"这条路径里摘出来。

**✅ GPU 加速合成层：Chrome 10（2011 年 3 月）最早在 `about:flags` 里提供"GPU Accelerated Compositing"开关（当时默认关闭），此后数年逐步默认开启（没有单一权威的"正式启用"日期），web.dev 上 Paul Lewis 2013 年 3 月的文章是这套机制较权威的讲解——transform/opacity 的变化可以完全交给独立合成层在 GPU 侧处理，跳过主线程的 layout 和 paint**
但合成层的提升时机由浏览器隐式判断（比如用了 3D transform/video/canvas 会被提升），开发者没法显式声明"这个元素接下来要变化，请提前准备"。

**❓ 合成层提升的时机不受开发者直接控制，动画开始瞬间才临时提升，容易在第一帧出现卡顿**
需要一个显式的 CSS 属性，让开发者能提前告诉浏览器"这个元素接下来要变化"。

**✅ `will-change`（W3C CSS Will Change Module Level 1 首个工作草案 2014 年 4 月发布；Chrome 36/2014 年年中、Firefox 36/2015 年 2 月开始支持）：显式声明"这个属性接下来会变化"，让浏览器提前准备合成层**
避免动画开始瞬间才临时提升导致的卡顿。

**现状：transform/opacity 能被提升为独立合成层、直接在 GPU 侧处理，跳过 layout 和 paint 两步，是动画性能优化的首选属性；`will-change` 是提前"预热"的显式声明，但过度使用（给太多元素加 `will-change`）会占用额外显存，不是没有代价的**
