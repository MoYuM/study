可能导致内存泄漏的代码

- 全局变量
- 闭包
- DOM引用
- 时间监听未移除
- 循环引用
- 定时器未清理
- 使用插件的时候，没有销毁
- console.log

## 发展史（问题 → 方案的链条）

**❓ IE6/7 时代，JScript 引擎的 GC 和 DOM 的 COM 引用计数是两套互不感知的系统——DOM 节点和 JS 闭包互相引用会形成"跨堆循环引用"，两边都够不着，永远不会被回收**
微软 2003 年 1 月 MSDN Magazine《Web Q&A: Releasing Memory in JScript》一文承认并解释了这个问题：`new Object()` 由 JScript 的 GC 管理，`document.createElement` 创建的对象由 IE 的 DOM（通过 COM 实现，用引用计数）管理，二者互不感知，跨界的循环引用双方都无法单独回收——这个问题直到 IE8 才修复。这是"内存泄漏"作为前端工程问题被广泛意识到的起点。

**✅ 现代主流引擎（V8/SpiderMonkey/JavaScriptCore）统一采用标记-清除（配合分代收集）而非纯引用计数**
从 GC Roots 出发做可达性遍历，不可达的对象——哪怕内部构成多复杂的循环引用——都会被自然清扫掉。这从算法层面根治了"循环引用导致泄漏"这类历史遗留问题：只要从根节点不可达，环有多复杂都不影响回收。

**❓ 标记-清除解决了"循环引用不可回收"，但开发者依然无法直观知道"我的页面到底哪里在泄漏"——GC 算法正确，不代表开发体验可诊断**
需要工具把"内存里到底有什么、谁引用着谁"暴露给开发者看，而不是只能靠猜。

**✅ Chrome DevTools 堆快照（Heap Snapshot）：Chromium 官方博客 2011 年 5 月发布《Chrome Developer Tools: Put JavaScript memory under control》正式介绍**
可以在某个时间点给整个堆拍一张"快照"，列出所有存活对象及其引用链；两次快照做 Comparison 对比，能定位到"哪类对象只增不减"，进而顺着引用链找到是谁还在拽着它不放。

**❓ 静态快照能看"某一刻的内存构成"，但看不出"内存是怎么随时间、随交互变化的"——不知道该在什么时间点拍快照才能抓住泄漏**
需要一个能展示内存随时间连续变化趋势的视图。

**✅ Timeline/Performance 面板的 JS Heap 曲线（约 2011–2012 年前后随 DevTools 早期版本迭代加入，未查到具体官方发布公告日期）**
录制一段操作，堆内存曲线随时间起伏，GC 后能不能回落一目了然：正常内存是"涨了又回落"的锯齿状，泄漏则表现为持续爬升、GC 后也降不回去——这是排查内存泄漏最直观的第一道判断依据。

**❓ 就算 GC 算法能处理循环引用、工具也能看出泄漏趋势，开发者写业务代码时还是会不小心用"强引用"做缓存——比如把已经从页面移除的 DOM 节点当 key 存进 Map/对象里，导致它们永远"可达"、永远回收不了。这不是 GC 或循环引用的问题，而是该用弱引用的场景被写成了强引用**
语言本身没有提供"持有引用但不阻止回收"的机制。

**✅ WeakMap/WeakSet（ES2015，2015 年 6 月）+ WeakRef/FinalizationRegistry（TC39 2020 年 7 月进入 Stage 4，正式写入 ES2021）**
用 WeakMap 给 DOM 节点做缓存，节点从页面移除后即便还在 WeakMap 里"挂名"，只要没有其他强引用，依然会被正常回收——把"防止误留强引用"这件事从"开发者自觉"变成了"语言机制兜底"。

**现状：GC 算法（标记-清除）已经从根源上解决了"循环引用"这个历史遗留问题；现在的内存泄漏大多是业务代码里意外的强引用（未清理的事件监听、未失效的定时器、被全局变量/闭包/缓存意外持有的引用），排查手段也相应从"看引用计数对不对"变成了"用 Performance 曲线找异常增长趋势 + Memory 快照对比定位具体对象"**
