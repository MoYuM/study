大模型 API 慢、贵、不稳定、会被限流，要当生产依赖治理：

- 幂等：重试可能重复扣费/落库/执行工具，必须幂等设计。
- 重试：区分可重试（超时/5xx/限流）与不可重试（参数错），配指数退避 + 随机抖动。
- 限流：不能只看 QPS，还要 RPM/TPM/并发/上下文大小/租户预算。模型网关统一承担。

## 发展史（问题 → 方案的链条）

**❓ 早期分布式系统里，客户端超时重试可能导致同一操作被执行多次（比如重复扣款）**
非幂等的操作（比如"给账户加钱"）如果因网络问题客户端没收到响应就重试，服务端可能执行两次，造成重复扣费/入账。

**✅ 幂等键（idempotency key）：给每次逻辑操作一个唯一标识，Stripe 支付 API 的推广让这个模式成为行业标准（具体首次推出年份没有权威公开记录，但 2015 年的产品更新日志已在讨论其行为细节，说明当时已存在一段时间，约 2014-2015 年前后）**
客户端为每次业务操作生成唯一的幂等键随请求发送，服务端记录"这个键对应的执行结果"，同一个键再次到达时直接返回之前的结果，不重复执行底层操作。

**❓ 光有幂等还不够——网络失败后，客户端该怎么重试、多久重试一次？**
如果所有客户端都立刻重试或按固定间隔重试，短暂的服务过载会因大量重试请求同时涌入而恶化。

**✅ 指数退避（exponential backoff）：每次重试间隔翻倍，源头可追溯到 1970 年代的网络退避理论**
思路最早来自 Simon Lam 和 Leonard Kleinrock 1973 年前后关于自适应重传退避的理论研究；1976 年 Robert Metcalfe 和 David Boggs 在经典论文里把"二进制指数退避"用到以太网的冲突避免机制里；1983 年 IEEE 802.3 标准把"截断"版本（退避有上限）正式写进规范。这套"失败一次等久一点、再失败等更久"的思路后来被广泛用到网络请求重试场景。

**❓ 纯粹的指数退避仍有问题：如果许多客户端在同一时刻失败，它们会按相同的时间序列同时重试，造成第二波拥堵**
所有客户端的退避序列如果完全一致（都是失败后 1s、2s、4s……），它们的重试请求还是会同时抵达服务端，这就是"惊群效应"。

**✅ 指数退避 + 随机抖动（AWS 的 Marc Brooker，2015 年 3 月发表的 "Exponential Backoff And Jitter" 一文系统提出并比较了几种抖动策略）**
在退避时间上加入随机浮动，让不同客户端的重试时间错开，避免同时重试造成雪崩；这篇文章后来成为业界重试设计的标准参考。

**❓ 通用的 QPS/RPS 限流够用于大多数 API，但大模型 API 的真实资源消耗和请求次数关系不大**
OpenAI 于 2020 年 6 月宣布 GPT-3 API（当时是需排队申请的私有 beta，直到 2021 年 11 月才对所有人开放、不再需要等待名单）。大模型调用的真实算力成本主要取决于处理和生成的 token 数量，而不是请求次数——一个短请求和一个带长上下文、长输出的请求，请求数一样但资源消耗可能差几十倍。

**✅ RPM + TPM 双维度限流（至少从 2023 年 GPT-4 beta 时代的文档看，OpenAI 已明确采用 RPM+TPM 组合限流，而不只是传统 QPS；无法确认这个设计是否从 2020 年 GPT-3 上线时就已存在）**
限流除了看每分钟请求数（RPM），还要看每分钟 token 数（TPM），更贴近真实的算力消耗；生产系统里还会叠加并发数、上下文长度、租户预算等维度。

**现状：大模型 API 网关 = 幂等键（防重复副作用）+ 指数退避带抖动（防重试雪崩）+ RPM/TPM/并发/租户预算多维限流——前两者是几十年沉淀的分布式系统经验，后者是 LLM 特有的适配**
