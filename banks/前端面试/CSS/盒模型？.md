盒模型：元素由 content → padding → border → margin 四层由内到外组成，`box-sizing` 决定 `width`/`height` 是否包含 padding/border。

## 发展史（问题 → 方案的链条）

**❓ 浏览器大战时期，IE 和 W3C 规范对"width 到底该不该含 padding/border"意见不一致**
1990 年代末浏览器大战期间，IE（尤其是 IE5）实现的 `width` 把 padding 和 border 都算在内；而 W3C 的 CSS1/CSS2 规范定义的 `width` 只指 content 区域，不含 padding/border。同一段 CSS 代码在不同浏览器下渲染出的实际盒子大小不一样，是当时著名的跨浏览器兼容问题之一。

**✅ 开发者先用 Hack 绕开这个不一致**
Tantek Çelik 在 2001 年提出的 "Box Model Hack"，利用不同浏览器对 CSS 语法解析的差异，针对性地给不同浏览器喂不同的 `width` 值，让最终渲染效果趋于一致——这是纯粹的绕过手段，不是真正解决分歧。

**✅ IE6 引入 DOCTYPE 切换：quirks mode 与 standards mode**
IE6 允许通过页面顶部的 DOCTYPE 声明来决定用「怪异模式」（沿用旧 IE 的 width 含 border 行为）还是「标准模式」（遵循 W3C 规范），让开发者能主动选择渲染行为，不必再靠 hack 蒙混过关。

**❓ 但"哪种算法更好"本身没有标准答案——很多时候你就是想要 width 包含 border 的效果**
W3C 标准的 content-box 算法虽然统一，但实际布局中经常想要"改 padding/border 不影响盒子总宽度"这种效果（老 IE 那套算法反而更直观），而当时没法按需选择，只能整页二选一（quirks 或 standards）。

**✅ CSS3 正式引入 `box-sizing` 属性：把"IE 那套算法"收编为标准里的合法选项**
`box-sizing` 提供 `content-box`（标准算法，默认值）和 `border-box`（原 IE 那套算法）两个值，可以**逐元素**按需选择——曾经的浏览器实现分歧，变成了正式的、可选的标准特性。

**❓ 默认值仍是 content-box，但大多数布局场景下 border-box 的心智负担更小**
`content-box` 是规范默认（为了向后兼容早期 CSS），但"改 padding/border 会意外撑大盒子"这个特性，在实际布局中经常带来困惑和计算负担。

**✅ 社区惯例：全局重置为 border-box（Paul Irish，2012 年博文推广）**
`* { box-sizing: border-box }` 这种全局重置写法被广泛采纳（Paul Irish 2012 年那篇被频繁引用的博文是重要的推广节点），成为现代 CSS 项目里事实上的默认起点。

**现状：两种盒模型并存，border-box 是社区最佳实践，content-box 仍是规范默认值**
这段历史的有趣之处：曾经的浏览器不兼容"bug"（IE 的 width 算法），最后变成了被规范正式收编、且实际更受欢迎的标准特性。
