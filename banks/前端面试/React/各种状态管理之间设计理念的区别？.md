- Redux：单一 store、状态不可变、纯函数 reducer、中间件处理副作用；可预测、可调试，但模板代码多（RTK 简化）。
- MobX：响应式 + 可变状态，自动追踪依赖，心智负担小但可控性弱。
- Zustand：基于 hook、极简、无 Provider、按需订阅。
- Recoil / Jotai：原子化，细粒度响应式更新。
- Vuex / Pinia：Vue 生态，Pinia 更轻、TS 友好。

选型看：项目规模、是否需要严格可追溯、细粒度更新与心智模型偏好。

## 追问：不可变数据跟 React 渲染性能优化有什么关系？

React（尤其配合 `React.memo`/`PureComponent`/`useMemo`）判断"要不要重新渲染"时，默认用的是**浅比较（shallow comparison）**——比较新旧 props/state 的引用是否相同（`===`），而不是深度遍历比较内容。

- 如果状态是**可变**的（直接改原对象），修改前后的引用是同一个，浅比较会误判"没变化"，导致该更新的地方不更新（bug）。
- 如果状态**不可变**（每次更新都返回一个新对象/新数组），引用一定会变，浅比较能又快又准地判断出"这里确实变了，需要重渲染"。

不可变数据让"引用比较"这种 O(1) 的开销就能可靠地判断变化，不需要深度比较——这跟"可测试、时间旅行调试"是两个不同维度的好处，但都源于同一个设计选择。

## 发展史（问题 → 方案的链条）

**❓ 早期 React 应用组件层级一深，父子组件之间传 props 变得难以维护（prop drilling），且没有统一的数据流规范**
需要一种统一、可预测的方式来管理跨组件共享的状态。

**✅ Flux（Facebook，2014 年 4 月底 F8 大会演讲，同年 5 月 6 日官方博客正式发布《Flux: An Application Architecture for React》）：单向数据流架构——Action → Dispatcher → Store → View，视图不能直接修改 Store，只能通过 Action 触发**
建立了"状态变化必须走统一入口"这个核心约束，但 Flux 本身允许多个 Store、Dispatcher 机制复杂，实际项目里样板代码多、维护成本高。

**❓ Flux 模式虽然解决了数据流方向的问题，但多 Store + Dispatcher 的设计写起来依然繁琐**
需要一个更简化、心智负担更小的实现。

**✅ Redux（Dan Abramov，2015 年 6 月创建——最初是为 React Europe 大会准备一个关于热重载的演讲原型，随后 Andrew Clark 加入协作完善了中间件等机制；确实受 Elm 语言架构启发，Abramov 自述是 Clark 提出 reducer 组合模式后才意识到"这正是 Elm 架构"）：把 Flux 简化成单一 store、纯函数 reducer、不可变状态更新**
用"纯函数 reducer + 不可变数据"这套约束换来了可预测性、可测试性、时间旅行调试能力（且不可变数据能让 React 用浅比较可靠判断状态是否变化），但 action/reducer 这套模板代码写起来依然啰嗦。

**❓ Redux 的模板代码问题一直被诟病，同时不是所有场景都需要这种"强约束、全局单一 store"的重量级方案**
一部分开发者转向"响应式、心智负担更小"的替代方案；Redux 官方也在着手简化自己的模板代码。

**✅ 两条分支并行发展：MobX（Michel Weststrate，大约 2015 年发布，与 Redux 同期，起初叫"MOBservable"后改名，因不满 React 大量元素同时更新时的性能而转向 Observable 响应式思路）走"可变状态 + 自动依赖追踪"路线；Redux 官方团队则从 2018 年 2 月的实验性 Redux Starter Kit 起步，2019 年 10 月正式定名 Redux Toolkit（RTK）1.0，简化 Redux 自身的模板代码**
心智模型上，MobX 更接近"直接改数据、框架自动帮你更新视图"，Redux(Toolkit) 依然坚持"通过 action 描述意图、reducer 计算新状态"这套显式流程，只是把样板代码简化了。

**❓ React 16.3.0（2018 年 3 月 29 日）推出官方 Context API，本意是解决"不想为了传递一个简单状态就引入第三方库"的轻量场景，但 Context 有性能缺陷：任何一个值变化，所有消费该 Context 的组件都会重渲染，不管它们实际关不关心那个具体值**
需要一种"更新到具体哪个状态就只重渲染关心那个状态的组件"的细粒度更新机制。

**✅ 原子化状态管理：Recoil（Facebook，2020 年 5 月 React Europe 大会发布）和 Jotai（Daishi Kato，构思始于 2018 年 10 月受 React Hooks 发布启发，因不满 Recoil 的 atom 需要字符串 key 而在 2020 年 9 月公开宣布、2021 年 1 月正式发布 npm 包）都采用"原子（atom）"作为状态最小单元，组件只订阅自己用到的原子**
从"整个 Context 树广播"变成"按需精确订阅"，解决了 Context 的性能问题。

**❓ 上面这些方案都需要额外的样板设置（Provider 包裹、store 配置），对中小项目显得有点重**
需要一个"直接拿来就用、不用包 Provider"的极简方案。

**✅ Zustand（2019 年 4 月首次发布，最初并非 pmndrs 团队所创；2020 年 Daishi Kato 加入 Poimandres/pmndrs 团队接手维护，推动其成为主流库）：基于 hook 的极简 API，不需要 Provider 包裹，按需订阅**
把状态管理简化成"一个 hook"，是当前"轻量化"这条路线的代表。

**现状：Redux(RTK)/MobX/Context/Recoil-Jotai/Zustand 代表了状态管理设计理念光谱上的不同取舍——从"强约束可预测但样板多"（Redux）到"响应式心智负担小但可控性弱"（MobX）到"细粒度原子化"（Recoil/Jotai）到"极简 hook 化"（Zustand），没有绝对最优解，选型看项目规模和团队对约定/自由度的偏好**
