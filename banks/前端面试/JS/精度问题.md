`0.1 + 0.2 !== 0.3`：因为 IEEE 754 双精度浮点用二进制表示，十进制小数 0.1/0.2 无法精确表示，运算后产生误差（0.30000000000000004）。

解决：

- 用 `Number.EPSILON` 做容差比较：`Math.abs(a-b) < Number.EPSILON`。
- 放大为整数运算再缩小（乘 10^n）。
- `toFixed(n)` 控制精度后再比较。
- 高精度场景用 decimal.js / big.js。

## 发展史（问题 → 方案的链条）

**❓ 1980 年代前，不同硬件厂商的浮点数实现互不兼容——字长、精度、舍入方式、上溢下溢处理各不相同（IBM 大型机 base-16 归一化被戏称"wobbling precision"、DEC VAX 的 D/G 格式也不统一），同一份数值计算代码在不同机器上能跑出不同结果，数值软件没法移植**
需要一个跨厂商统一的浮点数表示和运算标准。

**✅ IEEE 754-1985 标准：William Kahan（1976 年受聘为 Intel 设计 8087 数学协处理器的数据类型与运算规则，1977 年把这套设计带入 IEEE 委员会并主导起草标准草案，因此被称为"浮点数之父"，获 1989 年图灵奖）主导设计的二进制浮点数标准，统一了跨厂商的表示方式（符号位/指数位/尾数位）**
但二进制（base-2）表示十进制小数时，0.1 这类十进制有限小数在二进制下会变成无限循环小数，尾数位数有限（双精度 52 位）必须截断，产生 `0.1+0.2!==0.3` 这样的误差——这是标准统一带来的代价，不是某个语言的 bug，几乎所有用 IEEE 754 的语言都有这问题。

**❓ 金融、货币计算等场景对精度零容忍，二进制浮点的截断误差不可接受，但 IEEE 754 作为跨硬件通用标准不能说改就改**
各语言开始在应用层/标准库层提供高精度十进制运算方案，绕开二进制浮点的截断问题。

**✅ Java 在 JDK 1.1（1997 年发布）引入 `BigDecimal`；Python 通过 PEP 327 在 Python 2.4（2004 年发布）引入 `decimal` 标准库模块；IEEE 754 本身也在 2008 年修订版里新增了 decimal32/64/128 三种十进制浮点交换格式作为可选项**
但 JavaScript 至今没有原生的高精度十进制类型，只有 `Number` 这一种二进制浮点数字类型。

**❓ JS 没有原生十进制类型，遇到精度敏感场景怎么办？**
社区用 userland 库补位：`decimal.js`（Michael Mclaughlin 编写，2014 年首次发布）、`big.js` 等纯 JS 实现的任意精度十进制运算库，成为 JS 生态里事实上的"BigDecimal 替代品"。

**现状：二进制浮点（`Number`，硬件原生、速度快，但十进制小数有截断误差）与十进制高精度方案（`BigDecimal`/`decimal` 模块/`decimal.js`，精度优先但需要额外引入、性能有代价）并存——JS 目前仍只有前者是原生的，TC39 已有一个 Decimal 提案（基于 IEEE 754-2019 的 Decimal128 语义，Daniel Ehrenberg 与 Andrew Paprocki 领衔，动机就是解决金融计算里反复出现的浮点精度 bug），但截至 2025 年 4 月的 TC39 全会仍停留在 Stage 1，离真正进入 JS 语言规范还早**
